### 1.1 Why the release candidate moved from `96ebaad` to `5fd3775`

`96ebaad` (the squash-merge of PR #133) passed every code gate, and its tree was
byte-identical to the CI-verified PR head `0a5cf5d`. It was nevertheless **not
deployable**, which only a real deployment could reveal:

- **`29885a2` — API port.** A config-as-code `startCommand` on a Dockerfile service
  runs in exec form **without shell expansion**, so `--port $PORT` reached uvicorn as
  the literal string `$PORT`. The repository already documented this exact failure
  mode for the playground service; the API hit it independently.
- **`5fd3775` — web runtime mode.** `apps/web/app/layout.tsx` gained
  `export const dynamic = "force-dynamic"` so `MEMORYOPS_WEB_MODE` is evaluated per
  request rather than baked in at build time. This is **application source**, not
  configuration — without it the deployed web app renders the wrong mode.

`96ebaad` is therefore recorded as superseded rather than released. A tag pointing at
it would name a commit that was never successfully deployed, which is a weaker claim
than naming one that was.

### 1.2 Relationship between this commit and `5fd3775`

The §4 smoke evidence was collected against a deployment of **`5fd3775`**. This commit

is published in the GitHub Release body rather than edited back into this file — doing
so would create a further commit and restart the problem.

## 2. What v2.4 changes

v2.3 made mutations and evidence transactional. **v2.4 makes authority itself explicit
and enforceable across both the API and the web boundary.**

- Every exposed route carries a declared authorization contract; the matrix is
  *generated* from those declarations, not hand-maintained.
- Tenant authority and deployment authority are separated: no tenant role holds any
  `ops:*` permission, and `platform_operator` holds no customer-data permission.
- The web BFF enforces a capability contract **generated from the API's own
  authorization objects**, so the two cannot silently disagree.
- JWT role-claim states (omitted / null / empty / invalid) are distinguishable and
  fail closed — an issuer granting *no* roles is no longer confused with a credential
  that predates roles.
- Production deliberately minimizes its public surface.
- Structural regressions this repo has actually had are now CI-enforced.

### 3.2 Production startup gate — verified by refusal

The production profile is fail-closed, and that was confirmed by watching it *refuse
to boot* rather than by reading the code. Three separate refusals were observed:

- `storage='memory'` — no durability, no RLS
- `cors_allow_origins='*'` — any origin could call the API from a browser
- `auth_require_role_claim=false` — a credential with no roles would fall back to the default role
- `database_url` using bundled demo credentials / `localhost`

Each had to be resolved before the process would start. A deployment therefore cannot
silently run production with any of these.

These refusals were observed at `96ebaad`, not re-observed at `5fd3775`. The evidence
carries because the rules live in `services/api/app/core/config.py`, which is byte-for-byte
unchanged between the two commits — `git diff 96ebaad 5fd3775 -- services/api/app/core/config.py`
is empty. Every other row in §3 was re-run at `5fd3775` directly.

This was **not** a substitute for §4. It proved the harness and the boundary logic were
sound; it could not prove Railway's environment, proxy, TLS termination or managed
Postgres behave the same way. §4 establishes that.

Two observations came out of that run, and both were acted on:

- **`/metrics` was publicly reachable under the production profile.** That is the
  shipped default — the endpoint is content-free and low-cardinality, and most
  deployments scrape it over a private network. A Railway public hostname is not such
  an environment, so the deployment sets `MEMORYOPS_PROTECT_METRICS_ENDPOINT=true`,
  which requires `ops:metrics`. Confirmed in production as `401` (§4.1). The global
  default is deliberately unchanged in v2.4; this is deployment hardening, not a late
  API behaviour change.
- **Request validation runs before authorization.** An unauthorized caller posting a
  malformed body to a governance route receives `422` (schema detail) rather than `403`.
  No data leaks and a well-formed request from the same caller is correctly refused,
  but the schema is observable pre-authorization. Recorded as known behaviour (§6), not
  fixed in v2.4 — a fix would change API behaviour and did not belong in the RC.

## 5. Claims v2.4 **does** support

- Direct API authorization on every enforced route, generated from declarations rather than documented by hand.
- Separation of self / tenant / operator authority.
- Stored-record ownership authorization — the target user comes from the **stored** memory, never from the request body.
- JWT claim-state semantics: omitted / null / empty / invalid are distinguishable and fail closed.
- Actor-versus-target governance evidence.
- Web and API capability alignment, enforced by a generated artifact and a CI drift check.
- Zero unclassified routes; zero planned routes.
- Minimal production readiness output; interactive docs disabled by default in production.
- Repository structural regression guards, CI-enforced.
- Fail-closed production startup configuration.

## 6. Claims v2.4 **does not** make

Stated plainly so nobody has to infer the boundary:

- **Not** an "enterprise production-ready" certification.
- No SSO or SCIM.
- No customer-managed encryption keys.
- No complete backup / restore / disaster-recovery guarantee.
- No per-record ACL or ABAC system.
- No tenant-partitioned `/api/traces`.
- `GET /api/memories` remains **effectively self-scoped** — the query-string scope
  middleware binds it to the authenticated user. Administering another user's record
  goes through the governance-mutation path, not this collection route.
- No universal deletion / non-influence proof. The deletion guarantee is tested across
  retrieval, chat context and derived-artifact lineage; it is not a claim about every
  possible influence channel. (Bounded non-influence contracts are v2.8.)
- No worker fencing guarantee — a stale lease-holder is *unlikely* to commit, not yet
  *unable* to. (v2.6.)
- No complete live validation of every optional vector adapter; Qdrant / LanceDB /
  Weaviate are contract-tested, not live-service-tested.
- **Request validation precedes route authorization.** A malformed request from an
  unauthorized caller returns `422` rather than `403`, so request-schema detail is
  observable before authorization runs. No tenant data is exposed, and a well-formed
  request from the same caller is correctly refused.
- **`MEMORYOPS_AUTH_JWT_KEY` is not validated at startup.** With
  `MEMORYOPS_AUTH_MODE=jwt` and no signing key, the API boots cleanly under the
  production profile and then rejects every credential with `401`. The production
  readiness gate does not check for it.
- **The C1 worker check is weaker than it looks.** It asserts `/healthz/workers`
  returns 200, not that the body reports `healthy: true`. A deployment without
  `OPERATIONAL_DATABASE_URL` reports `healthy: false` and still passes C1. This
  release verified the body directly (§4.1); the harness gap is recorded, not fixed.
- **The smoke harness reports TLS trust-store failures as boundary failures.** A client
  without a CA bundle produces `CERTIFICATE_VERIFY_FAILED` on every request, which the
  harness surfaces as a dozen failed checks rather than one actionable error. It
  happened once during this release and was misleading for exactly as long as it took
  to read the detail lines.

The accurate one-line positioning:

> **A production-oriented governed-memory runtime with an explicitly tested API trust boundary.**
