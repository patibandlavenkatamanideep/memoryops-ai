### 1.1 Why the tag is a successor of the runtime RC

A release manifest cannot contain its own commit SHA, and it cannot contain evidence
generated after it was written. The runtime RC `5fef3ace` is what was built, deployed
and smoked; this commit adds only documentation on top of it.

The consequence, stated plainly so nobody has to infer it: **the tagged tree is not
byte-identical to the tree that produced the §4 evidence.** It differs by four
documentation files. §5 proves those files are not consumed as runtime source or
deployment configuration by any service, which is a weaker and more honest claim than
"identical image". The successor is rebuilt, redeployed and re-smoked before the tag
is published — that final result belongs in the Release body, not here.

passed while proving nothing:

## 5. Documentation-only successor — runtime equivalence

This commit changes exactly four files:

- `docs/releases/v2.5-release-truth.md` (this file)
- `CHANGELOG.md`
- `README.md`
- `docs/api-stability.md`

`CHANGELOG.md` and `README.md` sit at the repository root, so a path filter that merely
excludes `docs/` is **not** sufficient proof. The claim rests on what the services
actually consume:

- no change under `services/api/`, `services/worker/`, `apps/web/` or `railway/`;
- no Dockerfile, start command, environment-variable or configuration change;
- none of the four files is copied into an image as application source, and none is
  read at runtime by the api, worker or web service.

The supportable statement is therefore: **a documentation-only successor with
equivalent runtime source and configuration inputs.**

It is *not* a claim of byte-identical images, identical image digests, or zero
deployment risk. The successor is rebuilt and redeployed like any other commit, and is
re-smoked before the tag is published.

## 6. Claims v2.5 **does** support

- The real-Postgres RLS behavioural probe executes, runs as a non-superuser
  non-`BYPASSRLS` role, observes zero cross-tenant rows, and **fails closed** if it
  cannot run at all.
- Recorded real-provider Gemini extraction evidence is replayable offline from a
  committed cassette, with no credential and no network.
- External memory-system baselines execute reproducibly within their stated support
  boundaries, with `UNSUPPORTED` reported as a capability finding rather than a failure.
- Provider retries are classified: transient failures are retried, deterministic and
  permanent failures fail fast after a single attempt.
- Real Postgres/pgvector request-path behaviour was characterized, including the
  observed query plan at the measured data layout.
- Gemini 2.5 Flash provider-backed request-path performance was characterized under the
  tested workload and concurrency.
- The current measurements did not justify a blanket async migration.
- A full-history secret scan is currently clean: 209 commits, 0 findings.
- Repository release/status drift was reconciled against what actually shipped.

## 7. Claims v2.5 **does not** make

- **No** claim of universal superiority over other memory systems. On the four current
  deterministic probes a plain vector baseline also passes; those probes do not by
  themselves establish a governance advantage.
- **No** claim that Postgres retrieval always uses the ANN index, or is sub-linear in
  all data layouts. The planner's choice was observed to be data- and query-dependent.
- **No** claim that other providers behave like Gemini. Only `gemini-2.5-flash` was
  exercised live, at concurrency 1 and 5.
- **No** claim that async is never useful — only that these measurements did not
  justify a blanket migration.
- **No** claim that GIL serialization was proven; it was not separately measured.
- **No** production-scale or throughput guarantee. Performance figures are
  single-node laptop measurements and are not Railway-equivalent.
- **No** compliance certification, and no claim of zero security risk.
- **No** claim of complete persona-level authenticated Web/BFF session authorization.
  The C6 probes are unauthenticated; a signed-in tenant_admin being unable to reach
  operator routes still requires a manual session and remains future work.
- **No** claim that every production canary or control record was cleaned up — see §4.4.
- **No** claim that phase-gate documents were archived. They were deliberately
  **retained**: there was no archive convention to move them into, and
  `scripts/pr_invariant_gate.py` names their existing paths in enforced CI rules.
  Phase D reconciled and indexed repository truth; it did not archive those files.
